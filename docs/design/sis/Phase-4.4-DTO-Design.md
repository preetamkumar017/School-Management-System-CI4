# Phase 4.4 — SIS DTO Design (Revision 2)

**Revision 2 changes from Revision 1:** `CreateStudentRequest` (renamed in spirit to an internal `StudentStubData` shape, see below) finalized per ADR-004 — it is not a public API request DTO. `StudentSectionTransferRequest` confirmed to serve both first-assignment and later transfer (ADR-004 §4).

Convention: one Response DTO per entity (persisted fields only, no audit/version, the primary-key ID included); a `Create…Request`/`Update…Request` pair with CI4 Validation rules; a dedicated request DTO for any transition/action a BR gates on current persisted state. DTOs are plain PHP classes (or validated array shapes) in `App\Modules\Sis\DTOs` — never the raw Entity, per the Company Development Standard's response-envelope rule.

No Summary/Search DTO pair was added for `Student` or `Guardian` — no documented SIS list/search screen citation exists.

## `StudentStubData` — internal only, finalized (ADR-004; formerly drafted as `CreateStudentRequest`)

**Not a public API request DTO.** Per ADR-004 §3, `Student` stub creation is
reachable only through Admission's Confirm Enrollment orchestration calling
`StudentService::createStudentStub()` internally — there is no `POST /` on
`StudentController` that accepts this shape from a client.

| Field | Validation rule | Source |
|---|---|---|
| application_id | `required` | The `Application` being confirmed |
| admission_number | `required` | Generated by Admission (Phase 6) before this call |
| full_name | `required`, max length 100 | `Application.applicant_name` |
| dob | `required`, valid past date | `Application.dob` |
| category | `required`, in `{GENERAL, RTE}` | `Application.category` |
| aadhaar_number | optional, 12 digits | `Application.aadhaar_number`, if present |

`section_id` and `medical_info` are excluded — both remain `NULL` until FR-06 profile completion (ADR-004 §1).

## `UpdateStudentRequest` — unaffected

| Field | Validation rule |
|---|---|
| full_name | `required`, max length 100 |
| dob | `required`, valid past date |
| category | `required`, in `{GENERAL, RTE}` |
| aadhaar_number | optional, exactly 12 digits (concrete regex deferred to implementation) |
| medical_info | none (unbounded TEXT, optional) |

`section_id`/`application_id` excluded — `application_id` is immutable post-creation; `section_id` moves through `StudentSectionTransferRequest` (BR-SIS-005-gated, not a plain field edit).

## `StudentSectionTransferRequest` — unaffected in shape; dual-use confirmed (ADR-004 §4)

| Field | Validation rule |
|---|---|
| new_section_id | `required` |

Capacity check against destination section occupancy (BR-SIS-005) is a Service-layer concern. Per ADR-004 §4, this same DTO/operation serves **both** a stub's first section assignment during FR-06 profile completion **and** any later transfer.

## `StudentStatusChangeRequest` — unaffected

| Field | Validation rule |
|---|---|
| status | `required`, in `{DRAFT, ACTIVE, PROMOTED, EXITED, ARCHIVED}` |

Forward-only transition; DRAFT→ACTIVE gated by BR-SIS-003 and BR-SIS-006, both Service-layer concerns.

## `StudentResponse` — unaffected in shape

Fields: `student_id`, `admission_number`, `full_name`, `dob`, `aadhaar_number`, `section_id`, `application_id`, `category`, `status`, `medical_info`. No validation rules apply (Response DTOs never carry any). `section_id` may be `null` on a `DRAFT` record per ADR-004 — no structural change to this DTO results from that; it was always nullable in the response shape, only its DB-column nullability was previously unresolved.

## `CreateGuardianRequest` / `UpdateGuardianRequest` — unaffected

| Field | Validation rule |
|---|---|
| full_name | `required`, max length 100 |
| relationship | `required`, in `{FATHER, MOTHER, GUARDIAN, OTHER}` |
| mobile_number | `required`, exactly 10 digits (`regex_match[/^\d{10}$/]`) |
| email | valid email format, max length 100, optional |

## `GuardianResponse` — unaffected

Fields: `guardian_id`, `full_name`, `relationship`, `mobile_number`, `email`.

## `StudentGuardianLinkRequest` — unaffected

| Field | Validation rule |
|---|---|
| student_id | `required` |
| guardian_id | `required` |
| is_primary_contact | none, optional (defaults FALSE at entity level) |

Single request class — the link has no independently editable multi-field lifecycle. Duplicate-link rejection is a Service-layer check.

## `StudentGuardianLinkResponse` — unaffected

Fields: `student_id`, `guardian_id`, `is_primary_contact`.
